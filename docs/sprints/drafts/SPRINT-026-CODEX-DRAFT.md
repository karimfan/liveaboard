# Sprint 026: Open the Funnel, Portal, and Operations Spine

## Overview

Sprint 026 turns the Sprint 025 Triptych evaluation into a fixed
production posture and uses three product anchors to move Liveaboard
from internal charter administration toward a complete operator system:
public trip discovery, guest self-service, and crew/equipment readiness.

The resolved interview locks are binding. All three anchors ship in
one sprint. Stripe and payment processors are excluded. Deposits and
refunds are operator-confirmed offline records, mirroring Sprint 015's
folio checkout idiom: the platform records what the operator says
happened, but no money moves through Liveaboard. The production design
locks to `manta-night / spaces / living`; losing palettes, nav
renderers, and `full` motion remain in the tree for Sprint 027 cleanup.
The five named hero pages migrate to the component library this sprint:
Overview, Trips, TripDashboard, TripManifest, and GuestFolio.

## Use Cases

1. **Public trip inquiry.** A prospective guest opens
   `/charters/<org-slug>`, reviews published upcoming trips, and
   submits an inquiry with contact details, party size, date window, and
   notes.
2. **Quote acceptance without payment processing.** An Org Admin turns
   an inquiry into a quote, sends a link, the guest acknowledges "I will
   send deposit," and the operator manually records the offline deposit
   when it arrives.
3. **Berth hold.** Recording a confirmed offline deposit moves the
   quote/berth into `held` state for a clear expiration window. The
   platform stores payment method, amount, currency, received date, and
   operator notes, not processor tokens or card data.
4. **Guest portal.** A guest with a portal token sees itinerary,
   briefing materials, day plan, packing notes, equipment rental
   requests, dietary profile, certification upload/status, and their
   running folio.
5. **Trip-day portal.** When the trip is active, the same portal shows
   today's schedule/dive plan and the current folio state.
6. **Crew and equipment readiness.** An Org Admin manages crew roles,
   crew certifications, serialized equipment, service history, and sees
   trip readiness failures before confirming a trip.
7. **Locked production UI.** Production always renders
   `manta-night / spaces / living`, with no Triptych switcher or
   production URL/localStorage override. Dev can still inspect the
   losing options until Sprint 027.
8. **Hero page migration.** The daily-driver pages use
   `web/src/admin/components/` primitives and semantic tokens only:
   Overview, Trips, TripDashboard, TripManifest, GuestFolio.

## Architecture

### Scope Boundaries

In scope:

- Public catalog and inquiry flow.
- Operator-issued quotes.
- Guest quote acknowledgement link.
- Operator-confirmed offline deposits and refunds.
- Guest portal token routes that reuse and extend the existing guest
  registration/session patterns.
- Crew roster, crew certifications, serialized equipment, service
  history, and readiness gates.
- Design lock to `manta-night / spaces / living`.
- Component-library migration for exactly the five locked hero pages.

Out of scope:

- Stripe, Stripe Connect, webhooks, checkout sessions, refunds through
  a processor, card storage, PCI flows, POS integration, or payment
  links generated by a processor.
- Deleting losing Triptych palettes/layouts/motion modes.
- Migrating the other 17 legacy admin pages.
- Accounting export, marketing CRM, SOP/incident modules, photo
  gallery, survey automation, and post-trip booking automation beyond a
  visible CTA placeholder.

### Data Model

Add migration `internal/store/migrations/0021_sprint_026_funnel_portal_readiness.sql`.
Every operational table carries `organization_id` and every query
filters by it. Public lookup by slug is allowed only for published

```sql
-- Public funnel
ALTER TABLE organizations ADD COLUMN public_slug text NULL;
CREATE UNIQUE INDEX organizations_public_slug_idx
  ON organizations(lower(public_slug))
  WHERE public_slug IS NOT NULL;

ALTER TABLE trips
  ADD COLUMN published_at timestamptz NULL,
  ADD COLUMN public_title text NULL,
  ADD COLUMN public_summary text NULL,
  ADD COLUMN deposit_amount_cents bigint NULL CHECK (deposit_amount_cents IS NULL OR deposit_amount_cents >= 0),
  ADD COLUMN deposit_currency char(3) NULL,
  ADD COLUMN berth_hold_days integer NOT NULL DEFAULT 7 CHECK (berth_hold_days BETWEEN 1 AND 30);

CREATE TABLE leads (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references organizations(id) on delete cascade,
  trip_id uuid null references trips(id) on delete set null,
  email text not null,
  name text not null,
  party_size integer not null check (party_size between 1 and 50),
  date_window text null,
  notes text null,
  status text not null default 'new'
    check (status in ('new','quoted','closed','archived')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
CREATE INDEX leads_org_status_idx ON leads(organization_id, status, created_at desc);

CREATE TABLE booking_quotes (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references organizations(id) on delete cascade,
  lead_id uuid not null references leads(id) on delete cascade,
  trip_id uuid not null references trips(id) on delete cascade,
  token_hash bytea not null unique,
  guest_name text not null,
  guest_email text not null,
  party_size integer not null check (party_size > 0),
  quoted_total_cents bigint not null check (quoted_total_cents >= 0),
  deposit_due_cents bigint not null check (deposit_due_cents >= 0),
  currency char(3) not null,
  status text not null default 'sent'
    check (status in ('draft','sent','accepted','deposit_pending','held','cancelled','expired')),
  accepted_at timestamptz null,
  hold_expires_at timestamptz null,
  created_by_user_id uuid not null references users(id) on delete restrict,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
CREATE INDEX booking_quotes_org_trip_idx ON booking_quotes(organization_id, trip_id, status);

CREATE TABLE offline_payments (
  id uuid primary key default gen_random_uuid(),
  organization_id uuid not null references organizations(id) on delete cascade,
  quote_id uuid null references booking_quotes(id) on delete set null,
  trip_guest_id uuid null references trip_guests(id) on delete set null,
  direction text not null check (direction in ('deposit','refund')),
  amount_cents bigint not null check (amount_cents > 0),
  currency char(3) not null,
  method text not null check (method in ('bank_transfer','cash','wise','card_external','other')),
  received_on date null,
  reference text null,
  notes text null,
  recorded_by_user_id uuid not null references users(id) on delete restrict,
  recorded_at timestamptz not null default now()
);
CREATE INDEX offline_payments_org_quote_idx ON offline_payments(organization_id, quote_id, recorded_at desc);
```

`offline_payments` is intentionally not named `stripe_payments` or
`payment_intents`; it follows Sprint 015's "record offline settlement"
pattern. Totals are recomputed server-side from quote rows and payment
rows; client totals are display-only.

### Public Funnel Flow

Public endpoints are unauthenticated and rate-limited:

1. `GET /api/public/charters/{org_slug}` returns organization public
   profile plus published upcoming trips.
2. `GET /api/public/charters/{org_slug}/trips/{trip_id}` returns one
   published trip.
3. `POST /api/public/charters/{org_slug}/inquiries` validates input,
   creates a `leads` row, records audit metadata, and optionally emails
   the operator.
4. Staff lists and manages leads under `/admin/leads`.
5. Staff creates a quote from a lead and sends a token link.
6. `GET /api/public/quotes/{token}` shows the quote.
7. `POST /api/public/quotes/{token}/acknowledge-deposit` sets
   `status = deposit_pending` and records `accepted_at`.
8. Staff records the offline deposit with
   `POST /api/admin/booking-quotes/{id}/offline-payments`.
9. The server marks the quote `held`, sets `hold_expires_at`, and may
   create or update a `trip_guest` invite record for the held party.

No endpoint redirects to Stripe or creates payment links. The guest
acknowledgement copy must say the guest will send the deposit outside
Liveaboard; it must not imply Liveaboard has received money.

### Guest Portal Flow

The current guest registration surface uses guest invitation/session
patterns at `/guest/trips/:tripGuestId/register` and guest tab routes.
Sprint 026 adds a broader token/session portal under `/g/:token` in the
SPA and `/api/guest/portal/...` on the API side.

Portal sections:

- Overview: trip, boat, dates, itinerary, status.
- Pre-trip: briefing documents, packing list, equipment requests,
  dietary request, certification upload/status.
- On-trip: today's day plan and schedule when the trip is active.
- Folio: reuse the Sprint 015/Sprint 022 guest tab folio payload.
- Post-trip: digital dive log placeholder and "book next year" CTA only
  unless the data model is already cheap after the day-plan work.

The portal must never expose another guest's data through tampered
`trip_guest_id` or token values. Use opaque 404s for foreign or expired
tokens, matching existing guest route behavior.

### Readiness Gates

Sprint 018 created trip lifecycle transitions. Sprint 026 extends the
gate before a trip moves into operationally confirmed/started state:

- Required crew roles are assigned.
- Required crew certifications are present and not expired on the trip
  start date.
- Required equipment assets are in service.
- Tanks/O2/service-tracked equipment are not past service/VIP due dates
  on the trip start date.

The existing `planned | active | completed | cancelled` status model
does not currently include `confirmed`. Add `confirmed` only if the
implementation wants a pre-start readiness state; otherwise enforce the
gate on `POST /api/admin/trips/{id}/start` and expose readiness warnings
on TripDashboard/Trips. If `confirmed` is added, update every status
check, report, filter, and test that assumes the four-value enum.

## Definition of Done

- [ ] A guest can open `/charters/<org-slug>`, see only published
      upcoming trips, and submit an inquiry.
- [ ] An Org Admin can create/send a quote from a lead.
- [ ] A guest can open the quote link and acknowledge they will send an
      offline deposit.
- [ ] An Org Admin can record an offline deposit, after which the quote
      moves to held state with `hold_expires_at`.
- [ ] An Org Admin can record an offline refund as a platform record
      only; no processor integration exists.
- [ ] No Stripe SDK, webhook handler, checkout-session endpoint,
      processor payment link, card token, or PCI-sensitive field is
      introduced.
- [ ] Guest portal shows itinerary, briefing/day-plan content,
      equipment/dietary requests, certification upload/status, and
      running folio.
- [ ] Crew roster, crew certifications, equipment assets, and service
      events are manageable by Org Admins.
- [ ] Readiness failures for expired certs or out-of-service/service-due
      equipment block trip confirmation/start.
- [ ] Overview, Trips, TripDashboard, TripManifest, and GuestFolio
      render through `web/src/admin/components/` primitives and semantic
      tokens.
- [ ] Production locks to `manta-night / spaces / living`; the
      Triptych switcher and URL/localStorage overrides are dev-only.
- [ ] Losing palettes/nav renderers/`full` motion remain for Sprint 027;
      they are not deleted in Sprint 026.
- [ ] `web/src/styles/app.css` is smaller than 30 KB.
- [ ] Public endpoints are rate-limited and validate untrusted input.
- [ ] New store and handler tests prove multi-tenant isolation.
- [ ] `go test ./...`, `go vet ./...`, `npm run build`, and Prettier on
      touched frontend files pass.

## Security Considerations

- Public inquiry and quote endpoints are rate-limited and validate all
  user input.
- Quote and portal tokens are high-entropy, stored hashed, and compared
  without leaking foreign records.
- Public catalog endpoints expose only explicitly published trips and
  minimal organization profile data.
- Offline payment records must not store card numbers, CVV, processor
  tokens, bank credentials, or sensitive remittance documents.
- All admin mutation endpoints enforce Org Admin role unless an
  existing Cruise Director read-only rule applies.
- Every query against operational rows includes `organization_id`.
- Guest portal routes use opaque 404s for invalid, expired, or foreign
  tokens and trip guest IDs.
- Readiness gates recompute server-side inside lifecycle transitions;
  client readiness state is advisory only.
- Uploaded briefing/certification files keep the Sprint 017 document
  access checks and content-type/size restrictions.
