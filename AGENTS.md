# Liveaboard — Agent Guide

Canonical instructions for **all** AI agents working in this repo
(Claude Code, Codex, etc.). `CLAUDE.md` and `CODEX.md` are thin pointers
to this file — edit guidance here, not there.

Multi-tenant SaaS platform for scuba diving liveaboard operators. The
product centers on organizations, boats, trips, cruise directors, guest
manifests, onboard consumption, catalog pricing, per-boat stock, and
checkout currency quoting.

## Tech Stack

- **Frontend:** TypeScript, React, Vite (`web/`).
- **Backend:** Go (stdlib + minimal dependencies).
- **Database:** PostgreSQL (multi-tenant with row-level security).

## Key Requirements

- Online by default (offline support may be revisited later).
- Multi-tenant with strict data isolation between organizations.
- Real-time ledger tracking of guest consumption during trips.
- Designed for fast-paced crew environments.

## Environment

- Local development only for now — everything runs on the developer's
  machine; PostgreSQL runs locally. Cloud deployment (AWS/GCP) comes
  later.

## Read First — Sprint Ledger

Before doing any work, ground yourself in the sprint ledger. It is the
canonical record of what has shipped, what is in flight, and what is
planned next. Do not infer project state from filenames or memory alone.

1. Run `go run docs/sprints/tracker.go list` to see every sprint and its
   status (`planned`, `in_progress`, `completed`, `skipped`).
2. Read every `docs/sprints/SPRINT-NNN.md` for the latest 2–3 sprints
   (and any sprint marked `in_progress`). Each lists what was built, the
   architecture decisions, and the Definition of Done.
3. Skim `docs/product/organization-admin-user-stories.md` and
   `docs/product/personas.md` for the backlog and persona boundaries —
   these drive sprint scoping and role rules.
4. `docs/sprints/drafts/` holds the planning artifacts (intent → drafts
   → critique → merge notes) behind each final sprint doc.
5. Read `DESIGN.md` before touching frontend visuals.

When the code and an early sprint doc disagree, trust the code plus the
latest sprint docs.

```bash

make build    # production binary with embedded SPA

```

```bash

```

Tests use local PostgreSQL and skip cleanly when it is unavailable.
Default databases are `liveaboard` and `liveaboard_test`.

## Configuration

Config is **mode-based**, loaded by `internal/config/config.go`:

- `config/dev.env`, `config/test.env`, `config/production.env` —
  per-mode **non-secret** defaults (tracked).
- `.env.example` — template listing secret keys (tracked, no values).
- `.env.local` (repo root) — local secret/override values (gitignored);
  loaded for dev/test only.
- `web/.env.local` — generated by the Makefile from `VITE_*` keys for
  Vite to consume (gitignored).

Load order: `config/<mode>.env` → `.env.local` (dev/test) → process env
overlays. To add a key: declare it on the `Config` struct, then add the
non-secret default to each `config/<mode>.env` and/or the secret key to
`.env.example`. Do not commit real secrets to `config/*.env` (the lint
secret-scan enforces this).

## Design System

Always read `DESIGN.md` before any visual/UI decision; font choices,
colors, spacing, and aesthetic direction are defined there. Do not
deviate without explicit user approval. In QA mode, flag any code that
doesn't match `DESIGN.md`.

- **Cockpit, not Triptych (Sprint 027, ADR 0005).** The authenticated
  first screen is the Voyage Cockpit. Do not reintroduce runtime
  palette/layout switching, the floating design switcher, rail/canvas
  shell renderers, or `ui_redesign_switcher`. New admin UI plugs into
  the cockpit spine (role-scoped aggregate data, command palette routes,
  dense operational panels).
- **One palette, sea buttons, enforced (Sprint 028, ADR 0006).** The
  admin surface is one dark-sea semantic palette; all buttons are the
  sea family (`--btn-sea-*`; `Button` variants `primary` /
  `primaryGradient` / `primaryElectric`). Fonts are Inter (display/body)
  + JetBrains Mono (data).
- **Token contract.** Components and pages read semantic tokens
  (`var(--surface-*)`, `var(--text-*)`, `var(--accent-*)`,
  `var(--border-*)`, `var(--status-*)`) — never raw hex, never the
  legacy `--c-*` scale. New admin pages compose the component primitives
  + a co-located `*.module.css`. `font-family` uses `var(--font-*)` or
  `inherit`.
- **Enforced by Stylelint** (`color-no-hex` + `liveaboard/font-allowlist`)
  via `make lint` and `.github/workflows/ci.yml`. Raw hex lives only in
  `tokens.css` / `themes.css`.
- **`app.css` is legacy.** Do not add new dependencies on it. It serves
  only the light public/guest/auth pages pending migration; slated for
  deletion.

## Development Rules

- Code must compile before committing; tests written for changes and
  passing; `go vet` + linter clean; formatted (`gofmt` for Go,
  `prettier` for TypeScript). Each commit focused — no unrelated changes.
- Run the narrowest useful verification first, then broader checks
  (`make lint`, `make test`, `cd web && npm run build`) before handing
  off.
- **Tenant isolation:** every org-owned store query or mutation must be
  scoped by `organization_id`.
- **Role boundaries** from `docs/product/personas.md` must hold.
  Catalog/inventory/FX admin mutations require `org_admin`.
  Session-authenticated routes are shared by Org Admin and Cruise
  Director only when the product boundary allows it.
- Prefer existing helper APIs and local patterns over new abstractions;
  add focused tests for backend behavior, tenant isolation, validation,
  and authorization changes.
- Web visual/layout changes go through `web/src/admin/components/` +
  page-local CSS modules; see the Design System section.

## Branching

- **Work directly on `main`.** Do not create feature branches
  (`sprint-NNN-*`, etc.); each sprint or task lands as focused commits.
- **Do not open pull requests** unless the user explicitly asks; commits
  go straight to `origin/main`.
- The historical `sprint-NNN-*` branches on origin are archives only; do
  not base new work on them.

## Sprint Ledger Hygiene

When creating or completing sprint work:

```bash
go run docs/sprints/tracker.go sync
go run docs/sprints/tracker.go start NNN
go run docs/sprints/tracker.go complete NNN
```

Update the sprint doc with implementation notes, decisions, and
Definition-of-Done status when work materially advances a sprint.
